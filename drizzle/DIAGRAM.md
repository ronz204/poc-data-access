# Data model

Entity-relationship model of the PostgreSQL database, one Mermaid diagram per schema plus a global map of relations. Column lists are indicative and are finalized with the first migration.

## Schemas and tables

| Schema | Tables | Purpose |
|---|---|---|
| `platform` | `tenants`, `users`, `memberships`, `invitations`, `trailer` | Identity, tenancy, invitations to join a tenant, and the append-only audit trail. |
| `catalog` | `categories`, `products` | Sellable items and their stock. |
| `sales` | `customers`, `orders`, `items` | Purchases and their lines. |
| `wallet` | `accounts`, `entries` | Tenant balance and its immutable ledger. |
| `messaging` | `events`, `idempotency` | Outbox and idempotent request outcomes. |
| `reporting` | views only | Read-only projections for the query side, defined with the read queries. |

## Conventions

### Identifiers

- Every `id` is a UUID v7 generated by the application before the insert. There is no database default, so the id is known inside the use case (for the outbox, audit and idempotency records written in the same transaction) and ordering follows creation time.
- Tenant-scoped tables use a single-column `id` primary key. `tenant_id` is a separate indexed column, not part of the key.
- Composite primary keys appear only where the key is naturally the pair: `platform.memberships (tenant_id, user_id)`, `sales.items (tenant_id, order_id, product_id)`, `messaging.idempotency (tenant_id, key)`.

### Tenancy

- Every tenant-scoped table carries `tenant_id`, a foreign key to `platform.tenants`, and a row-level policy comparing it to the transaction's tenant setting.
- `platform.tenants` is the root and has no policy. `platform.users` is global: a user can belong to several tenants through `platform.memberships`.

### Types

| Concept | Type | Reason |
|---|---|---|
| Money | `bigint` in minor units (cents), one fixed currency | Exact integer arithmetic; no decimal-as-string handling in TypeScript. |
| Stock and quantities | `integer` with a check constraint | The database refuses negative stock whatever the concurrency strategy. |
| Timestamps | `timestamptz` | Unambiguous instants. |
| Free-form structured data | `jsonb` | Outbox payloads, idempotent responses, audit metadata. |
| Enumerations | `text` with a check constraint | Cheaper to evolve than a Postgres enum type. |

### Column suffixes and names

| Name | Meaning |
|---|---|
| `*_cents` | Money in minor units. |
| `*_snapshot` | Value copied at write time, independent of later changes to the source row. |
| `created_at` | Set once by the application at insert. |
| `updated_at` | Set by the application on every update, on mutable tables only. |
| `deleted_at` | Soft delete marker; `NULL` means live. |
| `version` | Integer incremented on every update, used for optimistic locking. |
| `reference_type`, `reference_id` | Origin of a record, held by type and id with no foreign key. |

### Constraints

- Soft-deletable tables (`catalog.products`, `sales.customers`) enforce uniqueness only on live rows through a partial unique index `WHERE deleted_at IS NULL`, so a deleted value can be reused.
- Immutable tables (`wallet.entries`, `platform.trailer`) have no `updated_at` or `deleted_at`; the application role can only insert and select. For `wallet.entries` that is the schema's default grant; `platform.trailer` sits in a writable schema, so its row-level policies allow only select and insert.
- Foreign keys cross schemas only toward `platform.tenants` and from `sales.items` to `catalog.products`. Wallet, messaging and the audit trail stay decoupled and refer to their origin by type and id.
- Order of list reads is `(created_at, id)`, so list tables index on `(tenant_id, created_at, id)`.

## platform

```mermaid
erDiagram
    tenants {
        uuid id PK
        text name
        timestamptz created_at
    }
    users {
        uuid id PK
        text email UK
        text name
        timestamptz created_at
    }
    memberships {
        uuid tenant_id PK, FK
        uuid user_id PK, FK
        text role "check: owner, admin, member"
        timestamptz created_at
    }
    invitations {
        uuid id PK
        uuid tenant_id FK
        uuid invited_by FK "to users"
        text email "invitee, may not be a user yet"
        text role "check: admin, member"
        text token_hash UK "hash only, never the token"
        text status "check: pending, accepted, revoked"
        timestamptz expires_at
        timestamptz created_at
        timestamptz accepted_at "null until accepted"
    }
    trailer {
        uuid id PK
        uuid tenant_id FK "nullable: actions with no tenant"
        uuid actor_id "nullable, no FK: null on system runs"
        text origin "check: name or name:detail"
        text action "check: entity.verb"
        text entity_type "no FK"
        uuid entity_id "nullable, no FK"
        jsonb metadata "default {}"
        xid8 xact_id "default pg_current_xact_id()"
        timestamptz occurred_at "default now()"
    }
    tenants ||--o{ memberships : has
    users ||--o{ memberships : joins
    tenants ||--o{ invitations : issues
    users ||--o{ invitations : sends
    tenants |o--o{ trailer : records
```

`tenants` has no row-level policy. `users` is not tenant-scoped.

`invitations` is tenant-scoped. The invitee is identified by email because the person may not have a user yet; accepting creates the membership (and the user if needed), so there is no foreign key to the invitee. Expiry is derived from `expires_at`, not stored as a status. A partial unique index on `(tenant_id, email) WHERE status = 'pending'` allows one open invitation per email and tenant, and the owner role can only be assigned through membership, never by invitation. Looking an invitation up by token happens before the tenant is known, so that read needs a dedicated path when row-level security lands.

`trailer` is the audit trail: one row per audited action, written in the same transaction as the change. `tenant_id` is nullable because some actions have no tenant at all (signing up a user); actions on a tenant from a platform context carry the affected tenant. `actor_id` is null on system runs, and `origin` always says which process wrote the row. `xact_id` groups the entries of one transaction. Row-level security allows the application role only select (rows of the current tenant) and insert (tenant, actor and origin must match the transaction settings), so rows are never updated or deleted. It is a candidate for monthly partitioning by `occurred_at`; if partitioned, the primary key becomes `(id, occurred_at)` because Postgres requires the partition key in every unique constraint.

## catalog

```mermaid
erDiagram
    categories {
        uuid id PK
        uuid tenant_id FK
        text name "unique per tenant"
        timestamptz created_at
    }
    products {
        uuid id PK
        uuid tenant_id FK
        uuid category_id FK "nullable"
        text name "unique per tenant among live rows"
        bigint price_cents "check >= 0"
        integer stock "check >= 0"
        integer version "optimistic lock"
        timestamptz created_at
        timestamptz updated_at
        timestamptz deleted_at "soft delete"
    }
    categories |o--o{ products : groups
```

`catalog` owns stock. Stock changes go through the concurrency strategy under evaluation, and the check constraint is the last line of defense.

## sales

```mermaid
erDiagram
    customers {
        uuid id PK
        uuid tenant_id FK
        text name
        text email "unique per tenant among live rows"
        timestamptz created_at
        timestamptz deleted_at "soft delete"
    }
    orders {
        uuid id PK
        uuid tenant_id FK
        uuid customer_id FK
        text status "check constraint"
        bigint total_cents "check >= 0"
        timestamptz created_at "keyset order with id"
    }
    items {
        uuid tenant_id PK, FK
        uuid order_id PK, FK
        uuid product_id PK, FK "to catalog.products"
        text name_snapshot "name at purchase"
        bigint price_snapshot_cents "price at purchase"
        integer qty "check > 0"
    }
    customers ||--o{ orders : places
    orders ||--|{ items : contains
```

`items` is the only table that references another schema besides `platform.tenants`: `product_id` points to `catalog.products`. The snapshots make an item independent of later product edits or deletion.

## wallet

```mermaid
erDiagram
    accounts {
        uuid id PK
        uuid tenant_id FK
        bigint balance_cents "materialized balance"
        integer version "optimistic lock"
        timestamptz created_at
    }
    entries {
        uuid id PK
        uuid tenant_id FK
        uuid account_id FK
        bigint amount_cents "signed"
        text reference_type "origin, no FK"
        uuid reference_id "origin, no FK"
        timestamptz created_at
    }
    accounts ||--o{ entries : records
```

`balance_cents` is updated in the same transaction that inserts the entry, so it always equals the sum of the account's entries. `entries` is an immutable ledger: insert and select only.

## messaging

```mermaid
erDiagram
    events {
        uuid id PK
        uuid tenant_id FK
        text type
        jsonb payload
        text reference_type "origin, no FK"
        uuid reference_id "origin, no FK"
        timestamptz created_at
        timestamptz delivered_at "null until delivered"
    }
    idempotency {
        uuid tenant_id PK, FK
        text key PK
        text request_hash
        jsonb response
        timestamptz created_at
    }
```

`events` is the outbox: an event is committed if and only if the change that produced it committed. A partial index on undelivered rows serves the polling query. `idempotency` allows one stored outcome per tenant and key.

## reporting

No physical tables. Read-only views and materialized views over the other schemas, defined together with the read queries and granted to the reader role only.
