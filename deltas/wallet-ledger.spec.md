# Wallet Ledger — Spec

> Each tenant's money balance as an append-only ledger whose entries explain every change, and a balance that can never be overspent or drift from its entries, even under concurrency.

## Intent

Sales credit the tenant, and the tenant can take money out or correct it. Whatever happens, two questions must always have a trustworthy answer: how much is there, and where did it come from. The ledger answers the second, the materialized balance answers the first, and the two are kept consistent in the same transaction. A debit that would overspend is refused even when many debits race, and history is never rewritten: a correction is a new entry that points at what it corrects.

## Scope

Owns:

- The tenant's account: one per tenant, in a single fixed currency, in minor units.
- The movements: sale credit, withdrawal, adjustment and reversal.
- Reading the balance and the entries.
- A reconciliation check.
- The tables `wallet.accounts` and `wallet.entries`.

Non-goals:

- Payments, payouts to real banks, currencies and exchange rates, interest and fees.
- More than one account per tenant, and transfers between tenants.
- A refund workflow. The reversal movement is its building block; the workflow itself is a future slice.
- Reports (sales-reporting slice).

## Contract

### Data model (target)

```
wallet.accounts(
  id            uuid primary key,
  tenant_id     uuid not null -> platform.tenants,
  balance_cents bigint not null check (balance_cents >= 0),
  version       integer not null,
  created_at    timestamptz not null
)
unique (tenant_id)

wallet.entries(
  id             uuid primary key,
  tenant_id      uuid not null -> platform.tenants,
  account_id     uuid not null -> wallet.accounts,
  amount_cents   bigint not null check (amount_cents <> 0),   -- signed
  reference_type text not null,                                -- origin, no foreign key
  reference_id   uuid not null,
  note           text null,                                    -- required reason on adjustments
  created_at     timestamptz not null
)
unique (tenant_id, reference_type, reference_id)
```

`note` is a planned column for the adjustment reason. (Assumed default.)

### Account

Created lazily by the first movement, in a tenant context, as a get-or-create inside that movement's transaction. A unique constraint on the tenant guarantees one account even when two first movements race: the loser reads the winner's row. The balance starts at 0. Creation is audited as `wallet.opened`. (Assumed default.)

### Movements

Every movement appends one entry and changes the balance in the same transaction.

| Movement | Who | Amount | Reference | Notes |
|---|---|---|---|---|
| Sale credit | Internal call from checkout, in the checkout actor's tenant context | Positive, equal to the order total | `order`, the order id | Not a user-callable action. A zero-total order writes no entry, because entries are nonzero. (Assumed default.) |
| Withdrawal | owner | Negative | `withdrawal`, a new id generated by the application | Fails when funds are insufficient. |
| Adjustment | owner | Positive or negative | `adjustment`, a new generated id | Requires a reason, stored in `note`. A debit fails when funds are insufficient. |
| Reversal | owner | Minus the original entry's amount | `reversal`, the id of the original entry | See below. |

Reversal rules:

- An entry can be reversed at most once.
- A reversal cannot itself be reversed.
- A reversal fails if it would make the balance negative, for example reversing a credit that was already spent.
- The original entry is never edited.

Withdrawal, adjustment and reversal require an idempotency key, with the mechanism of the idempotency-keys slice, because they move money. (Assumed default.) The sale credit relies on the idempotency of checkout.

### Balance protection

The balance changes with one conditional update:

```
balance_cents = balance_cents + :amount  WHERE balance_cents + :amount >= 0
```

The use case checks the affected rows. The check constraint on the balance is the last line of defense. There is no read followed by a write, and no long lock. Insufficient funds fail with an error that reports the available balance and change nothing. The `version` column increments on every balance change, but the strategy does not depend on it. (Assumed default.)

### Privileges

Entries are insert and select only for the application role; they are never updated or deleted, and that is enforced by privileges. The application role may update `wallet.accounts` only on the columns `balance_cents` and `version`, through a column-level grant in the migration that creates the table. (Assumed mechanism; the intent is that only the balance can change.)

### Reads

Owner and admin can read; a member cannot read the wallet.

- Get wallet: the balance.
- List entries: keyset paginated by `(created_at, id)` with a bounded page size and an optional filter by reference type.
- Reconciliation: a check that `balance_cents` equals the sum of the account's entries. It is used by tests and as an internal verification, not as a user use case.

### Audited actions

`wallet.opened`, `wallet.credited` (sale credit), `wallet.withdrawn`, `wallet.adjusted`, `wallet.reversed`. The allowlisted metadata is `amount_cents`, `reference_type`, `reference_id`, the balance after the movement and, for adjustments, the reason. The sale credit writes its own `wallet.credited` entry, separate from checkout's. (Assumed default.)

### Current state

Design only: there is no model, migration or code for the wallet yet.

## Invariants

- The balance is never negative.
- The balance always equals the sum of the account's entries.
- Entries are append-only: never updated, never deleted.
- Every entry is nonzero and refers to its origin by type and id, with no foreign key.
- An origin (type and id) produces at most one entry per tenant. This is what keeps the credit for an order to exactly once, even if the checkout code were retried.
- The credit for an order equals the order total.
- An entry is reversed at most once, and a reversal is not reversible.
- There is one account per tenant.
- Concurrent movements never overspend.
- A failed movement leaves no entry and no balance change.
- A tenant cannot read or move another tenant's wallet (row-level security, roadmap phase 8).

## Deferred / Open questions

- A refund workflow built on reversals.
- Whether to drop the `version` column, since the chosen strategy does not use it.
- Multiple currencies.
- Entry categories or a memo taxonomy.
- A running balance per entry or periodic snapshots, for fast statements.
- Partitioning or archiving old entries.
- Overdraft limits, and limits on withdrawal amounts.

## Acceptance criteria

Integration tests against a real PostgreSQL, using vitest once it is introduced:

- The first movement creates the account; two concurrent first movements create exactly one account.
- A sale credit appends one entry with reference `order` and the balance equals the total; a retried credit for the same order creates no second entry; a zero-total order creates no entry.
- 50 concurrent withdrawals whose total exceeds the balance: exactly the affordable ones succeed, the balance never goes negative and equals the sum of the entries.
- An insufficient-funds failure reports the available balance and changes nothing.
- An adjustment requires a reason and records it; an adjustment debit beyond the balance fails.
- A reversal appends the inverse entry referencing the original; reversing the same entry twice fails; reversing a reversal fails; reversing a credit that was already spent fails.
- Only an owner can withdraw, adjust or reverse; an owner and an admin can read; a member cannot.
- The application role cannot update or delete entries, and can update only `balance_cents` and `version` on accounts.
- Reconciliation holds after a mix of concurrent movements.
- A failure after the entry insert rolls back the entry and the balance together.
- Replaying a withdrawal with the same idempotency key does not debit twice.
- Another tenant cannot read this tenant's wallet.
